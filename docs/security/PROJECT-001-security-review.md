**Owner:** Security Reviewer

---

## 1. Goal

Identify the security-relevant foundation decisions and constraints before the human developer implements the project bootstrap. Because PROJECT-001 contains no business logic or authentication, this review is limited to local development security, secret handling, input validation conventions, and CORS.

---

## 2. Trust Boundaries

- External clients (browser) are untrusted.
- The backend (`services/monolith`) and PostgreSQL run in the developer's local trust zone.
- No production secrets or cloud credentials are managed by the foundation.

---

## 3. Authentication and Authorization

### 3.1 Out of Scope

- JWT authentication, RBAC, password hashing, session management, and service-to-service authentication are **out of scope** for PROJECT-001.
- These will be introduced in a later Phase 1 feature task (see SPEC.md §34 and §37).

### 3.2 Foundation Implication

- No security filter chain should be configured yet.
- All endpoints (including `/actuator/health`) are publicly reachable in the local environment.
- When authentication is added later, the `local` profile must continue to support frictionless FE/BE development without breaking existing smoke tests.

---

## 4. CORS Policy for Local Development

### 4.1 Recommended Policy

- Allow CORS **only** in the `local` Spring profile.
- Restrict allowed origins to the frontend dev server:
  - `http://localhost:5173` (Vite default)
  - `http://localhost:3000` (if CRA or Next.js is chosen)
- Allowed methods: `GET`, `POST`, `PUT`, `DELETE`, `OPTIONS`.
- Do not allow credentials in CORS preflight unless authentication is later enabled.
- In all other profiles (`test`, `prod`, etc.), CORS should be disabled or explicitly narrowed.

### 4.2 Rationale

Vite's dev-server proxy already avoids CORS for paths under `/api` and `/actuator`. A narrow CORS config is a safety net for direct browser calls during debugging.

---

## 5. Secret Handling

### 5.1 Database Credentials

- Database URL, username, and password must be supplied through environment variables (e.g., `DB_URL`, `DB_USER`, `DB_PASSWORD`).
- No credentials may be committed to `application.yml`, `application-local.yml`, or source control.
- `application-local.yml` may reference the environment variables using Spring placeholders:
  ```yaml
  spring.datasource.url: ${DB_URL:jdbc:postgresql://localhost:5432/flashsale}
  spring.datasource.username: ${DB_USER:flashsale}
  spring.datasource.password: ${DB_PASSWORD:}
  ```
- A `.env.example` file (without real values) may be committed as documentation, but `.env` files must be listed in `.gitignore`.

### 5.2 Test Profile

- The `test` profile should use Testcontainers PostgreSQL with autogenerated credentials.
- No real passwords are needed for tests.

### 5.3 Other Secrets

- No API keys, cloud credentials, or signing keys are required for PROJECT-001.

---

## 6. Input Validation Conventions

- Adopt Jakarta Bean Validation (`@Valid`, `@NotNull`, `@Size`, etc.) for all request DTOs from the first feature onward.
- Frontend should use native HTML validation and TypeScript types as a first line of defense, but never rely on frontend validation alone.
- Enforce a reasonable default request body size limit in Spring Boot to prevent trivial DoS via oversized payloads.

---

## 7. Logging and Data Leakage

- Do not log database passwords, connection URLs containing credentials, or stack traces at INFO level in production-like profiles.
- The health endpoint response may expose limited status information; avoid adding custom sensitive details to `/actuator/health`.

---

## 8. Abuse Scenarios

| Abuse | Risk | Mitigation |
|---|---|---|
| Local CORS config copied to production | Unrestricted cross-origin access. | Profile-gated CORS; review `local` vs. `prod` configs. |
| Hardcoded DB password committed | Credential leak. | Externalize secrets; use `.env.example`; audit `.gitignore`. |
| Oversized request to health endpoint | Minor local DoS. | Default Spring request size limits. |
| Port scanning on local dev ports | Information disclosure. | Bind to `localhost` only; do not expose dev servers to `0.0.0.0`. |

---

## 9. Verification Requirements

- [ ] No database password or secret is present in committed configuration files.
- [ ] CORS is active only in the `local` profile and restricted to local frontend origins.
- [ ] `.gitignore` excludes `.env` files and local IDE/build artifacts.
- [ ] `/actuator/health` does not leak internal identifiers or stack traces.
- [ ] A future threat-modeling session is scheduled when authentication is introduced.
