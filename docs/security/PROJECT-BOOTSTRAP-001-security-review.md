## 1. Goal

Identify the security-relevant foundation decisions and constraints before the human developer implements the project bootstrap. Because PROJECT-BOOTSTRAP-001 contains no business logic or authentication, this review is limited to local development security, secret handling, input validation conventions, and CORS.

---

## 2. Trust Boundaries

- External clients (browser) are untrusted.
- The backend (`services/monolith`) and PostgreSQL run in the developer's local trust zone.
- No production secrets or cloud credentials are managed by the foundation.

---

## 3. Authentication and Authorization

### 3.1 Out of Scope

- JWT authentication, RBAC, password hashing, session management, and service-to-service authentication are **out of scope** for PROJECT-BOOTSTRAP-001.
- These will be introduced in a later Phase 1 feature task (see SPEC.md §34 and §37).

### 3.2 Foundation Implication

- No security filter chain should be configured yet.
- All endpoints (including `/actuator/health`) are publicly reachable in the local environment.
- When authentication is added later, the `local` profile must continue to support frictionless FE/BE development without breaking existing smoke tests.

---

## 4. CORS Policy for Local Development

### 4.1 Recommended Policy

- Allow CORS **only** when `app.cors.enabled=true` is set, which is configured in the `local` Spring profile.
- Restrict allowed origins to the frontend dev server:
  - `http://localhost:5173` (Vite default)
- Allowed methods: `GET`, `POST`, `PUT`, `DELETE`, `OPTIONS`.
- Do not allow credentials in CORS preflight unless authentication is later enabled.
- In all other profiles (`test`, `prod`, etc.), CORS should be disabled or explicitly narrowed.

### 4.2 Rationale

Vite's dev-server proxy already avoids CORS for paths under `/api` and `/actuator`. A narrow CORS config is a safety net for direct browser calls during debugging. The explicit property gate reduces the risk of accidentally enabling CORS in a non-local profile.

---

## 5. Secret Handling

### 5.1 Database Credentials

- Database URL, username, and password must be supplied through environment variables (e.g., `DB_URL`, `DB_USER`, `DB_PASSWORD`).
- No credentials may be committed to `application.yml`, `application-local.yml`, or source control.
- `application-local.yml` may reference the environment variables using Spring placeholders:
  ```yaml
  spring.datasource.url: ${DB_URL:jdbc:postgresql://localhost:5432/flashsale}
  spring.datasource.username: ${DB_USER:flashsale}
  spring.datasource.password: ${DB_PASSWORD:}
  ```
- Provide an `.env.example` file (without real values) as documentation.
- `.env` files must be listed in `.gitignore` and never committed.
- Document the `.env` workflow in setup instructions (copy `.env.example` to `.env`, fill in values, source it or configure the IDE).

### 5.2 Test Profile

- The `test` profile should use Testcontainers PostgreSQL with autogenerated credentials.
- No real passwords are needed for tests.

### 5.3 Other Secrets

- No API keys, cloud credentials, or signing keys are required for PROJECT-BOOTSTRAP-001.

---

## 6. Input Validation Conventions

- Adopt Jakarta Bean Validation (`@Valid`, `@NotNull`, `@Size`, etc.) for all request DTOs from the first feature onward.
- Frontend should use native HTML validation and TypeScript types as a first line of defense, but never rely on frontend validation alone.
- Enforce a reasonable default request body size limit in Spring Boot to prevent trivial DoS via oversized payloads.

---

## 7. Logging and Data Leakage

- Do not log database passwords, connection URLs containing credentials, or stack traces at INFO level in production-like profiles.
- The health endpoint response may expose limited status information; avoid adding custom sensitive details to `/actuator/health`.
- The minimal request-id filter may log the request id in MDC; ensure it does not log other headers or bodies that could contain sensitive data.

---

## 8. Abuse Scenarios

| Abuse | Risk | Mitigation |
|---|---|---|
| Local CORS config copied to production | Unrestricted cross-origin access. | Property-gated CORS (`app.cors.enabled=true`); review `local` vs. `prod` configs. |
| Hardcoded DB password committed | Credential leak. | Externalize secrets; use `.env.example`; audit `.gitignore`. |
| `.env` file committed | Credential leak. | Add `.env` to `.gitignore`; verify with CI or pre-commit checks. |
| Oversized request to health endpoint | Minor local DoS. | Default Spring request size limits. |
| Port scanning on local dev ports | Information disclosure. | Bind to `localhost` only; do not expose dev servers to `0.0.0.0`. |

## 10. Updates Based on Final Technical Decisions

The following updates were made to this security review after the human developer resolved the Human Technical Decision Gate:

1. **Environment configuration:** The human decided to provide `.env.example` and document the `.env` workflow. This review now explicitly requires `.env.example`, `.env` in `.gitignore`, and documented setup steps.
2. **Local PostgreSQL:** Docker Compose is the recommended path, but developer-managed PostgreSQL is supported. Both paths must externalize credentials through the same environment variables.
3. **Request ID / MDC:** Only a minimal backend request-id filter is included. It must not log bodies, query parameters, or sensitive headers. Frontend interceptor, structured logging, and full observability are deferred.
4. **HikariCP:** Spring Boot defaults are used. No pool configuration secrets or tuning parameters are introduced.
5. **CORS:** Confirmed to use an explicit property gate (`app.cors.enabled=true`) in addition to the `local` profile.
